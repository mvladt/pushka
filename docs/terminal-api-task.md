# Задача: полный цикл планирования уведомления из терминала

> Тип документа — то, что в продуктовой терминологии называют **PRD** (product requirements
> document), для эпика — **epic brief**: «что хотим и почему», без «как реализуем». В конвенции
> этого репозитория такой документ — `*-task.md`; парный к нему «как» — `terminal-api-plan.md`.

## Проблема

Сейчас запланировать уведомление из терминала теоретически можно (`POST /api/notifications`
принимает JSON), но практически — нет: в теле обязателен объект `subscription`, а получить его
можно **только в браузере**, через `PushManager.subscribe()`. Это не наше архитектурное решение,
а физическое ограничение Web Push: подписку выдаёт push-сервис браузера (FCM, Mozilla, WNS) в
ответ на явное разрешение пользователя, и никакой HTTP-запрос из терминала её не породит.

Единственный существующий способ добыть подписку — открыть `pushka.mvladt.ru`, разрешить
уведомления и достать объект из DevTools. Для человека — терпимо один раз, для агента в
терминале — неприемлемо.

## Целевой воркфлоу

Однократное связывание (pairing), затем — сколько угодно уведомлений одним `curl`.

**Шаг 1. Агент создаёт pairing-сессию**

```sh
curl -sX POST 'https://pushka.mvladt.ru/api/pair'
# → {"pairingId":"vJ8n…","pairingUrl":"https://pushka.mvladt.ru/?pair=vJ8n…","expiresAt":"…"}
```

**Шаг 2. Человек открывает `pairingUrl` в браузере и разрешает уведомления**

Страница подписывается на push и кладёт полученный `subscription` в сессию
(`PUT /api/pair/:pairingId`). Это единственный шаг, требующий человека, — и он не устраним.

**Шаг 3. Агент опрашивает сессию, пока не получит подписку**

```sh
mkdir -p ~/.pushka
until curl -s "https://pushka.mvladt.ru/api/pair/$PAIRING_ID" \
    | jq -e '.subscription' > ~/.pushka/subscription.json.part; do
  sleep 2   # пока status=pending, ключа .subscription нет и jq -e выходит с ненулевым кодом
done
mv ~/.pushka/subscription.json.part ~/.pushka/subscription.json
```

Пишем во временный файл и переименовываем в конце намеренно: `> file` обрезает цель **до** того,
как отработает `jq`, поэтому наивный однострочник, запущенный слишком рано, затёр бы уже
имеющуюся подписку. Цикл выходит по TTL сессии — если человек не открыл ссылку за 10 минут,
`GET` начнёт отдавать `404` (тогда `jq -e` тоже не найдёт ключ, и это стоит различать в реальном
скрипте — готовый рецепт с обработкой ошибок даём в README).

**Шаг 4. Дальше — сколько угодно уведомлений, без браузера**

```sh
curl -sX POST 'https://pushka.mvladt.ru/api/notifications' \
  -H 'Content-Type: application/json' \
  -d "$(jq -n --slurpfile sub ~/.pushka/subscription.json '{
        datetime: "2026-08-01T09:00:00+03:00",
        payload: { title: "Стендап", body: "Через 5 минут" },
        subscription: $sub[0]
      }')"
# → 201 {"id":"018f…"}
```

Шаги 1–3 делаются один раз на устройство. Подписка живёт у вызывающей стороны (файл, переменная
окружения, секрет CI) и передаётся в каждом запросе.

## Функциональные требования

| №   | Требование                                                                                     |
| --- | ---------------------------------------------------------------------------------------------- |
| 1   | `POST /api/pair` создаёт сессию и возвращает `pairingId`, `pairingUrl`, `expiresAt`            |
| 2   | `GET /api/pair/:pairingId` возвращает `{"status":"pending"}` либо `{"status":"ready", …}`      |
| 3   | `PUT /api/pair/:pairingId` принимает `subscription` от браузера                                |
| 4   | Страница-клиент в режиме `?pair=<id>` после подписки сама отправляет `PUT`                     |
| 5   | `POST /api/notifications` возвращает `201` с телом `{"id": "…"}` — id генерирует **сервер**    |
| 6   | Тело `POST /api/notifications` валидируется: формат `subscription`, `datetime`, размер payload |
| 7   | `datetime` от API-клиента требует явной таймзоны (`Z` или `±hh:mm`)                            |
| 8   | Rate limit по IP и ограничение горизонта планирования                                          |
| 9   | Все ответы API — JSON, пригодный для `jq`; README и OpenAPI содержат рабочие curl-рецепты      |

## Принятые решения

**Сессии pairing хранятся в памяти процесса, не в SQLite.** Живут 10 минут, теряются при
рестарте — и это нормально: потерянная сессия означает «спарься заново», а не потерю данных.
Ключевое следствие: **эпик не меняет схему БД вообще** (id генерируется сервером в уже
существующую колонку), а значит не зависит от `docs/sqlite-migrations-task.md` и не требует
миграции на проде. Это главная причина, по которой эпик остаётся маленьким. Допущение —
однопроцессный сервис под systemd (зафиксировано в `sqlite-migrations-task.md`); при появлении
нескольких инстансов сессии придётся вынести в общее хранилище.

**Подписка отдаётся по `pairingId` повторно, сессия удаляется по TTL, а не по первому чтению.**
Основной потребитель — агент, поллящий в цикле; при «выдать ровно один раз» любой сбой ниже по
конвейеру (`jq` упал, запись в файл не прошла) безвозвратно сжигает pairing. Реальная защита
здесь — не одноразовость, а энтропия `pairingId` (≥128 бит, `crypto.randomUUID()`) плюс короткий
TTL, который в любом случае убивает утёкшую ссылку.

**`id` уведомления генерирует сервер.** Сейчас id приходит от клиента, а в хранилище стоит
`INSERT OR REPLACE` (`src/sqliteStore/store.ts:28`) — то есть любой, кто пошлёт `id: "123"`
(буквально пример из README), затрёт чужое уведомление. При открытом `POST` и сторонних
пользователях перезапись — единственная доступная атака на чужие данные, и закрывается она
одной строчкой. Присланный клиентом `id` игнорируется (не ошибка — чтобы не ломать старые
вызовы). Плата: контракт ответа меняется с пустого `201` на `201` с телом, вместе с ним едут
браузерный клиент, интеграционные и e2e-тесты.

**`datetime` без таймзоны от API-клиента не принимается.** `validateDatetime.ts:9` пропускает всё,
что парсит `new Date()`, включая голое `2026-01-01T12:00`, а `store.ts:61` разрешает такую строку
как **локальное время сервера**. Для браузера, стоящего рядом с сервером, это незаметно; для
агента в другой таймзоне — тихая ошибка на несколько часов, и именно этот агент теперь основной
потребитель API. Мы не фиксируем и не документируем TZ прод-сервера — вместо этого требуем явный
offset. Браузерный клиент уже шлёт `.toISOString()`, его это не задевает.

**Rate limit — свой мидлвар в памяти, не nginx `limit_req_zone` и не библиотека.** Двадцать строк,
ноль зависимостей, работает в dev и покрывается интеграционными тестами; конфиг nginx не покрыт
ничем.

## Явно вне объёма

- **CLI-обёртка `pushka`** — поставляем только HTTP API и curl-рецепты.
- **Скилл для агента** — собирается на стороне потребителя, в репозиторий не входит.
- **Чтение/изменение/отмена уведомлений** (`GET`, `PATCH`, `DELETE` — сейчас заглушки `500`).
  Эпик закрывает только создание. Отмена — очевидный следующий кандидат, но она требует
  авторизации: без неё `DELETE /api/notifications/:id` даёт удаление чужого по угаданному id.
- **Авторизация** — `POST /api/notifications` остаётся открытым.
- **Белый список доменов push-сервисов.** `subscription.endpoint` — произвольный URL, который
  сервер дёргает сам (SSRF-образная находка из `docs/security-review-result.md`). Осознанно
  оставляем как есть, но фиксируем: эпик превращает этот открытый `POST` в документированный
  интерфейс для сторонних пользователей, то есть экспозиция находки растёт.

## Критерий приёмки

E2E-тест (`tests/playwright/push-cycle.spec.ts`) проходит полный цикл: `POST /api/pair` → браузер
открывает `?pair=<id>` и разрешает уведомления → поллинг `GET /api/pair/:id` отдаёт подписку →
`POST /api/notifications` с этой подпиской → push доставлен. Пока этот сценарий зелёный,
воркфлоу из терминала действительно работает; curl-рецепты в README — производная от него,
а не самостоятельное доказательство.
