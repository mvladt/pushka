# Задача: валидация тела `POST /api/notifications`

## Проблема

`createNotificationRouter` (`src/router/notificationRouter.ts:15`) берёт `req.body` и приводит
его к `NotificationEntity` через `as` — TypeScript-приведение типов, которое ничего не проверяет
в рантайме. Дальше объект без изменений уходит в `scheduler.schedule()` и сохраняется в SQLite.
Отсутствие валидации уже отмечено открытым `TODO` в `src/scheduler/scheduler.ts:13`:
`// TODO: Добавить какую-то валидацию. В частности на 'schedule' и 'cancel'.`

В момент отправки (по таймеру) `notification.subscription` целиком передаётся в
`webpush.sendNotification()` (`src/pusher/pusher.ts:12`) — без проверки, что `subscription.endpoint`
принадлежит домену легитимного push-сервиса (`fcm.googleapis.com`,
`updates.push.services.mozilla.com`, `web.push.apple.com` и т.п.). Библиотека `web-push` сама
такую проверку не делает.

**Практическое следствие:** тот, кто может POST-нуть на `/api/notifications`, может подставить
`endpoint`, указывающий на внутренний адрес или адрес во внутренней сети сервера — и сервер сам
сделает туда исходящий HTTP-запрос в момент отправки. Это SSRF-образная поверхность, подтверждена
чтением кода (не гипотеза).

### Калибровка серьёзности (не переоценивать)

- **Слепой (blind) SSRF.** `POST /api/notifications` отвечает `201` сразу (line 18), отправка
  происходит позже по таймеру, `sendOne` только логирует `statusCode` и глотает ошибки — ответ
  до атакующего никогда не доходит. Это разведка/проверка доступности внутренней сети, не эксфильтрация данных.
- **Форма запроса ограничена.** Тело — это зашифрованный `web-push`-пейлоад с фиксированными
  заголовками, а не произвольный POST с контролируемым телом — нельзя послать осмысленную команду
  внутреннему сервису, только непрозрачные байты на URL.
- **Кража метаданных облака (`169.254.169.254`) — не проверено, не факт.** Прод — голый VPS
  (не факт, что провайдер вообще отдаёт metadata-сервис на этом IP) — не стоит фиксировать это
  как подтверждённый вектор без проверки на самом сервере.
- Риск живёт **уже сейчас**, не «вырастет вместе с проектом» — это не гипотетический сценарий на
  будущее, а существующий пробел.

## Желаемое поведение

- На границе `POST /api/notifications` — рантайм-валидация тела (как минимум структура
  `NotificationEntity`, включая обязательные поля подписки).
- Отдельно — allowlist доменов `subscription.endpoint` по известным push-сервисам (FCM, Mozilla
  autopush, Apple). Это отдельная и, вероятно, более важная проверка, чем просто структурная
  валидация — именно она закрывает SSRF-вектор.
- Заодно закрыть общий `TODO` в `scheduler.ts:13` (валидация `schedule`/`cancel`).

## Связь с другими решениями

- В `docs/cicd.result.md` (этап 4.2, CodeQL) отмечено, что этот конкретный поток данных
  (`req.body` → запись в SQLite → чтение по таймеру → `sendNotification`) пересекает границу
  персистентности в БД — стандартный taint-tracking CodeQL по умолчанию такую цепочку, скорее
  всего, не поймает. Находка сделана ручным код-ревью, не аргумент в пользу подключения CodeQL.
