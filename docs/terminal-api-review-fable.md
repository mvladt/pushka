# Ревью идеи terminal-api (Fable 5)

Ревью `terminal-api-task.md` + `terminal-api-plan.md` на коммите `2d48dda`, 2026-08-12.
Все фактические утверждения доков сверены с кодом (список — в конце).

## Вердикт

Идея зрелая, границы эпика выбраны правильно, факт-чек почти чистый. Pairing-флоу — верное
решение неустранимого ограничения Web Push, а «подписка живёт у вызывающей стороны» — самый
дешёвый из работающих вариантов (сервер не хранит ничего дольше TTL, схема БД не трогается).
До старта работ стоит поправить одну фактическую ошибку в task и закрыть два пробела в плане;
плюс два решения, которые предлагаю пересмотреть.

## Ошибка в task: поллинг-цикл не выходит по TTL — он зависает навсегда

`terminal-api-task.md`, шаг 3: «Цикл выходит по TTL сессии — если человек не открыл ссылку за
10 минут, `GET` начнёт отдавать `404`». Это неверно для приведённого сниппета:

```sh
until curl -s "…" | jq -e '.subscription' > …; do sleep 2; done
```

`until` крутится, **пока команда падает**. На `404` тело не содержит `.subscription`, `jq -e`
выходит с ненулевым кодом — и цикл продолжается вечно, а не завершается. TTL здесь убивает
сессию на сервере, но не цикл у агента. Правка минимальная — либо честно написать «наивный
цикл на протухшей сессии зависнет, различайте 404 в реальном скрипте», либо сразу показать
цикл с проверкой HTTP-кода (`curl -w '%{http_code}'` или `-f`). Раз README обещает «готовый
рецепт с обработкой ошибок», рабочая версия всё равно понадобится — но и иллюстративный
сниппет не должен содержать ложное утверждение о собственном поведении.

## Пробелы в плане

**1. Ужесточение `validateDatetime` сломает существующие unit-тесты хранилища.**
`store.saveOne()` зовёт `validateDatetime` (`src/sqliteStore/store.ts:55`), а
`createFakeNotification` в `tests/tools.ts:15` по умолчанию отдаёт голое `"2025-01-01T00:00"` —
ровно тот формат, который этап 2 начнёт отклонять. Тесты `npm run test:sqliteStore` упадут.
В этапе 2 нет чекбокса про обновление `tests/tools.ts` и тестов хранилища — добавить, иначе
сюрприз всплывёт посреди этапа. Заодно решить, где живёт ужесточение: если только в новом
валидаторе роутера (а `validateDatetime` в store остаётся мягким), тесты не задеты — но тогда
пункт плана «`src/validateDatetime.ts` — требовать явную таймзону» указывает не на тот модуль.

**2. `PUT /api/pair/:pairingId` принимает `subscription` без валидации.**
Этап 2 валидирует только тело `POST /api/notifications`, этап 4 про валидацию `PUT` молчит.
Если браузер (или кто угодно — ручка открыта) положит в сессию мусор, агент честно заберёт
его в файл и будет получать ошибки уже на шаге 4, вдали от причины. Переиспользовать
валидатор `subscription` из этапа 2 — одна строка, добавить чекбокс в этап 4 и негативный
интеграционный тест.

## Предлагаю пересмотреть

**1. Выкинуть `pairingUrl` и `PUBLIC_ORIGIN` целиком.** Самый тяжёлый хвост эпика — env-пере-
менная с тремя следствиями (дефолт, тесты env, инъектируемость через `createTestApp`) плюс
ручной шаг «дописать в прод-`.env` до деплоя» с риском не поднявшегося сервиса. Всё это — ради
строки, которую вызывающая сторона собирает сама: агент **знает** origin, по которому только
что сделал `POST /api/pair`. Ответ сокращается до `{ pairingId, expiresAt }`, рецепт в README —
`echo "https://pushka.mvladt.ru/?pair=$PAIRING_ID"`, e2e-тест собирает URL из порта, который и
так знает. Исчезают: пункт про `PUBLIC_ORIGIN` в этапе 4 (примерно треть этапа), шаг в этапе 6,
класс ошибок «прод-`.env` разошёлся с кодом». Плата — API чуть менее самодокументируемый;
формат URL фиксируется в README/OpenAPI. По-моему, размен однозначно выгодный — это ровно тот
минимализм, на котором держится весь эпик («не трогаем схему БД» из той же серии).

**2. Allowlist доменов push-сервисов — забрать в этап 2, а не оставлять за бортом.** Task
осознанно откладывает его, честно фиксируя рост экспозиции. Но перекрёстное ревью
(`docs/decisions.md`, 2026-08-10) уже поставило allowlist вторым шагом порядка работ — сразу
после серверного `id`, который этот эпик как раз делает. Этап 2 и так проверяет
`subscription.endpoint` как https-URL; дотянуть до сверки hostname со списком известных
push-сервисов — считанные строки в уже написанном валидаторе, и SSRF-находка из
`security-review-result.md` закрывается в том же PR, который увеличивает её экспозицию.
Трейд-офф: список надо поддерживать (FCM, Mozilla, `web.push.apple.com`, WNS — у WNS домены
вида `*.notify.windows.com`), экзотический браузер может не пройти. Для проекта с известным
кругом потребителей это слабый контраргумент. Если всё же откладывать — тогда хотя бы завести
issue, чтобы решение не потерялось между доками.

## Мелкие замечания

- **Кап на число pairing-сессий.** Хранилище сессий в памяти + открытый `POST /api/pair` =
  рост памяти под спамом. Rate limit по IP помогает, но распределённый источник его обходит.
  Одна константа (`MAX_SESSIONS`, при переполнении — `503`) закрывает вопрос.
- **Чистка протухших сессий — при `create()`, без таймера.** «Периодическая чистка» из этапа 4
  требует интервал, его остановку в `stop()` и тест на таймер. Ленивая проверка TTL в `get()`
  плюс подметание при каждом `create()` дают тот же результат без фонового процесса.
- **Ретраи стали неидемпотентными.** Побочный эффект серверного `id`, не отмеченный в task:
  раньше повтор запроса с тем же `id` перезаписывал запись (`INSERT OR REPLACE`), теперь
  повтор после сетевого таймаута создаст дубль уведомления. Для агента, который ретраит
  `curl`, это реальный сценарий. Принять осознанно (и упомянуть в README-рецепте), не чинить.
- **Тихое протухание подписки.** Подписка в `~/.pushka/subscription.json` — бессрочный
  bearer-объект, но браузер может её отозвать/ротировать. Тогда агент получает `201`, push
  не приходит, а обратной связи нет (`GET /api/notifications` — заглушка `500`, pusher глотает
  ошибки). Неустранимо в рамках эпика, но README обязан назвать симптом и лечение:
  «уведомления перестали приходить → спарьтесь заново».
- **`429` — тоже JSON.** Требование 9 task («все ответы API — JSON») в плане явно раскрыто
  только для `400`; проследить, чтобы rate-limit-ответ не оказался `text/plain`.
- **Текст pairing-страницы должен называть последствие.** Страница в режиме `?pair=` привязывает
  устройство к терминалу, приславшему ссылку. Человек, открывший чужую ссылку, должен понимать,
  что разрешает: «это устройство будет получать уведомления от запросившего терминала» — одна
  фраза в этапе 5 против фишинг-сценария «просто разреши уведомления».
- **Лимит `express.json` — глобальный.** `~4 КБ` из этапа 2 должен учитывать, что в том же теле
  едет `subscription` (~300–500 байт) и JSON-обвязка; брать потолок с запасом (например, 8 КБ
  на тело при отдельной проверке размера `payload`), иначе легитимный запрос упрётся в лимит.

## Что явно хорошо

- Ломающее изменение контракта (`id`) — первым этапом, остальное строится на новом.
- Отказ от одноразовости pairing-сессии с внятным обоснованием (энтропия + TTL вместо
  «сжечь при первом чтении») — правильный разбор реального режима отказа.
- Пункт про реальный IP за nginx в этапе 3 — ровно та ловушка, которую обычно находят уже на
  проде; здесь она поймана на этапе плана.
- Критерий приёмки — e2e полного цикла, а не «curl-рецепты написаны»; README как производная
  от зелёного теста.
- «Явно вне объёма» с объяснением *почему* (отмена требует авторизации) — редкая гигиена.
