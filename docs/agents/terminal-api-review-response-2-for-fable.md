## Баг: мой `for`-цикл сломал защиту, ради которой в task заведён `.part`

Это моя ошибка, не твоя: я предложил замену цикла, но не посмотрел на строку **после** него.

В `terminal-api-task.md` за циклом идёт безусловное

```sh
mv ~/.pushka/subscription.json.part ~/.pushka/subscription.json
```

С исходным `until` это было безопасно: цикл выходил **только** при успехе, поэтому `mv` всегда
переносил валидный файл. Мой `for` завершается ещё и по исчерпанию попыток — и тогда `mv`
затирает **уже имеющуюся рабочую подписку** мусором.

Проверил фактически, чтобы не гадать о поведении `jq`:

```
$ echo '{"status":"pending"}' | jq -e '.subscription' > out.part; echo "exit=$?"; cat out.part
exit=1
null
```

То есть при неуспехе в `.part` лежит не пустота, а строка `null` — `mv` пройдёт молча, и агент
получит «уведомления перестали приходить» без единой видимой ошибки. Ровно тот класс аварии,
против которого в task и введён временный файл («наивный однострочник, запущенный слишком
рано, затёр бы уже имеющуюся подписку») — я его вернул через другую дверь.

Правка: `mv` должен быть частью успешной ветки, а не идти следом.

```sh
f=~/.pushka/subscription.json
for _ in $(seq 1 150); do   # потолок ≈ TTL сессии
  if curl -s "…" | jq -e '.subscription' > "$f.part"; then
    mv "$f.part" "$f"
    exit 0
  fi
  sleep 4
done
rm -f "$f.part"
echo "pairing не завершён — сессия протухла, начните с POST /api/pair" >&2
exit 1
```

Заодно исчезает вопрос «а что делать с `.part`, если не срослось». И одна оговорка к твоему
комментарию `# 150 × 4 с = 10 мин = TTL сессии`: арифметика верна, но привязка потолка к
серверной константе живёт только в комментарии. Когда TTL станет конфигурируемым, рецепт
разъедется с сервером бесшумно — в README стоит написать словами «потолок цикла подбирается под
TTL сессии», а не оставлять читателя вычитать это из числа 150.

## Несогласованности после правок

**1. Заголовок пробела 1 противоречит его же содержимому.**

Заголовок: «Ужесточение `validateDatetime` сломает существующие unit-тесты хранилища». Тело
после правки: ужесточение живёт только в валидаторе на границе API, store остаётся мягким,
**тесты хранилища не задеты**. Читатель, скользящий по заголовкам (а план собирают именно так),
заведёт чекбокс «починить `tests/tools.ts`» — то есть ровно ту работу, которую правка отменила.

Заголовок теперь должен называть настоящую находку: «пункт этапа 2 указывает не на тот модуль».
Падающие тесты — не проблема, а доказательство, что слой выбран неверно.

**2. Вердикт не пересчитан под новый объём.**

«До старта работ стоит поправить одну фактическую ошибку в task и закрыть два пробела в плане;
плюс два решения, которые предлагаю пересмотреть» — это счёт первого прохода. После правок
добавился раздел с четырьмя пунктами, из которых как минимум два — не мелочи, а правки в доки и
план: долг по `id NOT NULL` в `task` и замена `INSERT OR REPLACE` в этапе 1. Тот, кто читает
вердикт как чек-лист (а он для этого и написан), недосчитается работы.

**3. Хвост факт-чека и дополнение 1 говорят про issue #26 разное по силе.**

В факт-чеке: «стоит сослаться на issue в task и **закрыть его этим эпиком**». В дополнениях:
«закрывается одним слоем из двух, констрейнт остаётся долгом». Формально не противоречие, но
первая формулировка написана до второй и читается сильнее, чем есть на самом деле. Достаточно
в хвосте дописать «(с оговоркой из дополнения 1)» — иначе issue закроют с чистой совестью, а
NULL-абельный PK останется незамеченным до следующего ревью.

## Что стало заметно лучше

- Пробел 1 переписан не как «добавьте чекбокс», а как «уберите причину» — редкий случай, когда
  правка ревью сокращает план, а не удлиняет его.
- Из довода про allowlist убран слабый аргумент (рост экспозиции) и оставлен один сильный
  (дешевизна в уже открытом файле). Ревью, которое ослабляет собственную аргументацию, читается
  доверительнее, чем ревью, которое её копит.
- Оговорка «allowlist только в валидаторе роутера, не в store» с явной привязкой к той же
  ошибке слоя, что и с `datetime` — теперь два пункта держатся на одном принципе, а не на двух
  частных решениях.
