## Что проверил из нового

Ты добавил в порядок внедрения яруса 0 обоснование, которого в моей критике не было:

> без этого клейм по `id` не работает — `WHERE id IN (...)` не матчит NULL

Прогнал на `node:sqlite`:

```
заклеймлено строк: 1 из 3
статусы: [{"id":null,"status":"pending"},{"id":null,"status":"pending"},{"id":"a","status":"claimed"}]
```

Верно. Следствие даже жёстче, чем сформулировано: NULL-строки не просто не клеймятся — они
навсегда застревают в `pending` и продолжают попадать в подзапрос каждый проход. То есть
статусная модель без `NOT NULL` не только не чинит баг, а консервирует его в новой форме.
Хорошее самостоятельное наблюдение, стоило бы усилить формулировку.

Prettier на файле проходит.

## Осталось поправить

### 1. Строка 177 — прямое противоречие исправленному пункту 4

```
- **SRP** — в основном да, с двумя нарушениями: валидация в store (должна быть на границе)
```

Пункт 4 теперь говорит, что проверка в store должна **остаться** как assert инварианта
«`datetime` — канонический UTC-ISO». Раздел SOLID по-прежнему числит её нарушением SRP.
Читатель, дошедший до SOLID, получит ровно ту рекомендацию «перенести», от которой уводит
пункт 4 — и, выполнив её, сломает инвариант, на котором держится лексикографическое
сравнение в SQL.

**Предлагаю:** оставить в списке нарушений SRP только `createApp` (`express` + `getPort`
наружу), а про валидацию сказать отдельно — «валидация входа отсутствует на границе»
(отсутствие проверки в роутере, а не наличие проверки в store).

### 2. Строка 204 — тот же хвост в оценке уровня

В перечне признаков junior+ осталось «валидация не в том слое». После уточнения это уже не
самостоятельный дефект — дефект в том, что на границе валидации нет вообще.

Заметнее другое: **в этом перечне нет `id: null`** — главной находки документа. Она
аргументирует тезис сильнее, чем всё остальное в списке (нестрогий tsconfig, 500 вместо
501): пропущенный NULL-абельный первичный ключ, назначаемый клиентом, — это ровно тот класс
ошибок, о котором раздел говорит.

**Предлагаю:** заменить «валидация не в том слое» на «`id` от клиента без проверки и
NULL-абельный PK» и/или дописать находку 3 в перечень.

### 3. Строка 421 — порядок внедрения расходится с разделом наблюдаемости

```
4. pino + prom-client + честный health + метрика лага.
```

Раздел «Наблюдаемость» теперь говорит: логи с уровнями можно вообще без зависимостей,
`pino` — только если захочется структурного JSON; а `/metrics` без сборщика — эндпоинт в
никуда, и порядок должен быть «после уровней логов и честного health». Шаг 4 всё ещё
называет pino обязательным и ставит prom-client вровень с health.

**Предлагаю:** «уровни логирования + честный health + метрика лага; `pino`/`prom-client` —
по необходимости, когда появится сборщик».

## Чего в ревью по-прежнему нет (не претензия, а наблюдение)

Ни `docs/decisions.md`, ни один другой документ не ссылается на `project-review-result.md`.
Документ на 400+ строк с пересортированным порядком работ и воспроизведённым багом висит вне
журнала решений. Вывод «валидация границы вперёд `strict`» и находка `id: null` без строки в
журнале через месяц потеряются в `docs/` — при том что журнал решений сам же назван в ревью
одной из сильнейших сторон проекта.

Отдельно: баг `id: null` тянет на GitHub issue по принятому в проекте issue-driven флоу —
воспроизводимый, дешёвый в починке, с security-последствиями (перекалибровка находок 1–2
`security-review-result.md`).
