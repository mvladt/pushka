# Отчёт: security-review `POST /api/notifications` (ручной, по ходу решения про CodeQL)

## Контекст

Возник по ходу решения — подключать ли CodeQL (`cicd.plan.md`, 4.2). Чтобы не гадать про ROI
статического анализа вслепую, прочитали код ключевого write-эндпоинта руками. Находки ниже —
результат этого чтения, не автоматического сканирования.

## Находка 1: `POST /api/notifications` открыт и не валидируется — корневая причина

- **Нет авторизации.** `createApp` (`src/app.ts`) вешает `cors()` без опций (разрешены все
  origin) и `router` без какого-либо auth-middleware. `createRouter`
  (`src/router/router.ts`) тоже ничего не добавляет. Эндпоинт открыт всем в интернете.
- **Нет валидации тела.** `createNotificationRouter` (`src/router/notificationRouter.ts:15`)
  берёт `req.body` и приводит его к `NotificationEntity` через `as` — TypeScript-приведение
  типов, ничего не проверяющее в рантайме. Открытый `TODO` в `src/scheduler/scheduler.ts:13`
  подтверждает, что это известный, но не закрытый пробел:
  `// TODO: Добавить какую-то валидацию. В частности на 'schedule' и 'cancel'.`

### Следствие: resource-exhaustion self-DoS (самый весомый риск из всех найденных)

Открытый неаутентифицированный write без валидации даёт два способа положить сам сервис, без
всякой игры с `endpoint`:

1. Забить SQLite мусорными записями до исчерпания диска.
2. Заказать пачку уведомлений на «сейчас». `getAllForNow` подхватывает все разом,
   `sendMany` (`src/pusher/pusher.ts`) делает `Promise.all` без ограничения параллелизма — если
   записи указывают на недоступные адреса, куча зависших исходящих соединений разом съедает
   файловые дескрипторы/память процесса и **задерживает или роняет доставку настоящих
   уведомлений живых подписчиков**. Атакующему для этого не нужна видимость результата —
   это удар по самой причине существования pushka (своевременная доставка).

## Находка 2: `subscription.endpoint` не валидируется — SSRF-образная поверхность

`notification.subscription` целиком уходит в `webpush.sendNotification()`
(`src/pusher/pusher.ts:12`) без проверки, что `endpoint` принадлежит домену легитимного
push-сервиса (`fcm.googleapis.com`, `updates.push.services.mozilla.com`,
`web.push.apple.com` и т.п.). Библиотека `web-push` сама такую проверку не делает.

### Калибровка серьёзности

- **Слепой SSRF только для *внутренних* адресов.** `POST /api/notifications` отвечает `201`
  сразу, отправка асинхронная по таймеру, `sendOne` только логирует `statusCode` и глотает
  ошибки — если `endpoint` указывает на внутренний адрес, ответ до атакующего не доходит.
  Разведка/проверка доступности, не эксфильтрация.
- **Не слепой, если атакующий указывает свой собственный сервер.** В этом случае он получает
  POST напрямую и видит: egress-IP пушки, точное время доставки, заголовки запроса (включая
  VAPID JWT — подписанный токен для конкретного origin, не приватный ключ; низкая ценность вне
  контекста FCM/автора).
- **Форма запроса ограничена** — тело это фиксированный `web-push`-зашифрованный пейлоад с
  фиксированными заголовками, не произвольный POST с контролируемым содержимым.
- Кража метаданных облака (`169.254.169.254`) **не проверена и не факт** — прод на голом VPS,
  неизвестно, отдаёт ли провайдер такой сервис вообще. Не утверждаем это как вектор.

### Use case'ы (по убыванию конкретности)

1. **Self-DoS** — тот же самый вектор, что в находке 1, только через `endpoint`-чёрную-дыру
   вместо просто мусорных записей. Не требует видимости результата.
2. **DDoS от имени пушки / отмывание атрибуции.** Не амплификация (примерно 1:1) — ценность для
   атакующего в том, что трафик светится с IP пушки, а не его, плюс можно запланировать
   скоординированный залп на точный момент через `schedule`. Реальный вред достаётся владельцу
   pushka: жалобы абузу, риск блокировки IP хостинг-провайдером.
3. **Слепая разведка/действие на внутренние сервисы** — самый слабый и теоретический пункт.
   Ограничено фиксированной формой пейлоада — может задеть только внутренние эндпоинты,
   реагирующие на любой POST независимо от содержимого.

## Находка 3: CORS открыт для всех origin

`app.use(cors())` без опций в `src/app.ts` разрешает запросы с любого origin. Статический клиент
раздаётся тем же Express-процессом (`express.static`), то есть в норме это same-origin —
не проверено, зачем вообще нужен permissive CORS. Не критично само по себе (эндпоинты и так
публичны и без авторизации), но избыточно и стоит пересмотреть вместе с находкой 1.

## Решение по CodeQL — не подключаем

Дефолтный taint-tracking CodeQL для JS/TS **не отслеживает поток через границу персистентности**
(`req.body` → запись в SQLite → чтение по таймеру → `sendNotification`) — то есть находки 1 и 2
выше он бы, скорее всего, не поймал в принципе. Находки сделаны ручным чтением кода. Раз
конкретный кейс, ради которого мог бы пригодиться SAST, CodeQL всё равно не покрывает — решение
не подключать (`cicd.plan.md`, п. 4.2) остаётся в силе на текущих основаниях: **низкий ROI для
проекта такого размера**, а не «нечего защищать». Пересмотреть при появлении рендеринга
сохранённого/пользовательского контента в HTML, admin-панели или более чувствительных данных.
