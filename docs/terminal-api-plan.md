# План: полный цикл планирования уведомления из терминала

Верхнеуровневый план к `docs/terminal-api-task.md`. Этапы идут в порядке зависимостей: 1–3 —
приведение существующего `POST /api/notifications` в состояние, пригодное для внешнего
потребителя; 4–5 — собственно pairing; 6–7 — приёмка и документация.

Схема БД не меняется ни на одном этапе — миграции (`docs/sqlite-migrations-task.md`) не нужны.

## Этап 0. Подготовка

- [ ] Завести issue на эпик со ссылкой на `docs/terminal-api-task.md`

## Этап 2. Валидация тела запроса и политика таймзон

- [ ] Модуль валидации `NotificationEntity`: `subscription.endpoint` — https-URL,
      `keys.p256dh`/`keys.auth` — непустые строки, `payload` — объект, `datetime` — обязателен
- [ ] Лимит размера payload (~4 КБ — потолок Web Push) и `express.json({ limit })` в `src/app.ts`
- [ ] `src/validateDatetime.ts` — требовать явную таймзону (`Z` или `±hh:mm`), отклонять голое
      `YYYY-MM-DDTHH:mm`; выверить, что браузерный клиент (шлёт `.toISOString()`) не задет
- [ ] Ответы на невалидное тело — `400` с JSON `{ "error": "…" }`, а не `text/plain`
- [ ] Unit-тесты валидации + интеграционные на `400`

## Этап 3. Лимиты

- [ ] **Разобраться с реальным IP клиента.** `nginx/pushka.conf` проксирует с `X-Real-IP`, но
      **без** `X-Forwarded-For`, а `trust proxy` в `src/app.ts` не выставлен — значит `req.ip`
      на проде равен `127.0.0.1` для всех запросов, и лимитер по IP молча станет глобальным.
      Либо добавить `X-Forwarded-For` в nginx + `app.set("trust proxy", …)`, либо читать
      `X-Real-IP` явно. Проверить на проде, а не только локально
- [ ] Мидлвар rate limit в памяти (окно + счётчик на IP) на `POST /api/notifications` и
      `POST /api/pair`, ответ `429`
- [ ] Горизонт планирования: `datetime` не в прошлом (с допуском под `GRACE_MS`) и не дальше
      заданного потолка вперёд
- [ ] Интеграционные тесты: `429` при превышении, `400` при выходе за горизонт

## Этап 4. Pairing-сессии

- [ ] `PUBLIC_ORIGIN` в `.env`/`.env.example` и `src/env.ts` — нужен, чтобы собрать `pairingUrl`
      (из `req` его надёжно не получить: за nginx `req.protocol` — `http`). Три следствия,
      которые надо учесть сразу, иначе всплывут в самый неудобный момент:
  - [ ] **Не делать переменную обязательной без дефолта.** Прод-`.env` лежит вне `releases/` и
        переживает деплой (`docs/cicd-result.md`) — новая обязательная переменная там сама не
        появится, и ближайший деплой просто не поднимет сервис. Либо дефолт из `PORT`, либо
        явный шаг «дописать `PUBLIC_ORIGIN` в прод-`.env` до деплоя» (см. этап 6)
  - [ ] Обновить `tests/env/env.test.ts` — он покрывает загрузку `.env`
  - [ ] Значение должно быть **инъектируемым**, а не читаться модулем на импорте: в e2e
        приложение слушает случайный порт (`app.getPort()`), и зашитый `PUBLIC_ORIGIN` разойдётся
        с адресом тестового сервера. Прокинуть через `createTestApp()` в `tests/tools.ts`
- [ ] Хранилище сессий в памяти: `create()`, `get()`, `attachSubscription()`, TTL 10 минут,
      периодическая чистка протухших
- [ ] `src/router/pairRouter.ts` — три ручки:

| Метод | Путь                   | Ответ                                                                         |
| ----- | ---------------------- | ----------------------------------------------------------------------------- |
| POST  | `/api/pair`            | `201 { pairingId, pairingUrl, expiresAt }`                                    |
| GET   | `/api/pair/:pairingId` | `200 { status: "pending" }` / `200 { status: "ready", subscription }` / `404` |
| PUT   | `/api/pair/:pairingId` | `204` / `404` несуществующая или протухшая / `422` мёртвая подписка           |

- [ ] Проверка подписки тестовым push прямо в `PUT`: инжектировать `pusher` в `pairRouter`,
      отправить «Pushka: связь установлена» и посмотреть статус от push-сервиса. `404`/`410` —
      подписку в слот не кладём, отвечаем ошибкой (человек в этот момент смотрит в телефон, это
      единственный момент, когда он может что-то починить). Прочие ошибки push-сервиса не должны
      валить связывание — логируем и считаем `PUT` успешным
- [ ] Подключить роутер в `src/router/router.ts`
- [ ] Unit-тесты хранилища сессий (в т.ч. протухание) + интеграционные на все три ручки

## Этап 5. Режим pairing на странице-клиенте

- [ ] `src/client/index.html` — при `?pair=<id>` в URL после успешной подписки отправлять

- [ ] Проверить, что обычный режим страницы (без `?pair`) не изменился — файл общий с e2e-тестом

## Этап 7. Скилл и документация

Скилл — витрина эпика: именно он, а не curl-рецепты, производит целевой воркфлоу. Держать
**минималистичным**: что это, три команды связывания, одна команда планирования, правило про
таймзону. Не пересказ README.

- [ ] `skills/pushka/SKILL.md` — исполняемая версия шагов 1–4:
  - [ ] печать `pairingUrl` **вместе с QR** (`qrencode -t ANSIUTF8`, при отсутствии утилиты —
        голый URL), иначе ссылку не перенести с ноутбука на телефон
  - [ ] поллинг ограниченным по времени циклом (~60 с — меньше таймаута команды у раннера
        агента), при неудаче — попросить человека и повторить, а не висеть до TTL
  - [ ] где искать подписку между сессиями: `PUSHKA_SUBSCRIPTION` → `~/.pushka/subscription.json`
        → иначе связывание. У облачных агентов файл не переживает контейнер, и без переменной
        «однократное связывание» станет ежесессионным
  - [ ] таймзона: относительное время считать от `date -u`, для абсолютного («завтра в 9 утра»)
        выяснять таймзону **человека** — своя у агента в контейнере обычно UTC
  - [ ] после связывания один раз спросить «уведомление пришло?» — доставку агент проверить не
        может, это единственный доступный сигнал
- [ ] `specs/api/openapi.json` — три ручки `/api/pair`, обновлённый ответ `201` у
      `POST /api/notifications`, новые коды `400`/`422`/`429`
- [ ] `README.md` — раздел «Из терминала»: рабочие curl-рецепты всех четырёх шагов, включая
      готовый цикл поллинга. Существующий пример переписать целиком, а не поправить: он шлёт
      `"payload": {"text": "Hello"}`, тогда как `src/client/sw.js` читает `title`/`body` (сейчас
      этот рецепт даёт уведомление «Уведомление» с пустым телом), а его `datetime` — ровно та
      форма без таймзоны, которую эпик запрещает
- [ ] `docs/decisions.md` — запись про pairing в памяти, серверный `id` и про то, что
      работоспособность подписки доказывает сервер при связывании, а не агент потом
- [ ] `docs/terminal-api-result.md` — что получилось, что отложили
- [ ] Перенести пару `terminal-api-plan.md` + `terminal-api-result.md` в `docs/archive/`

## Открытые вопросы к реализации

- Конкретные числа лимитов (запросов в минуту, горизонт планирования, TTL сессии) — подобрать
  на этапе 3–4, вынести в константы одного модуля, а не разбрасывать по коду.
- ~~Нужен ли признак «уже забрали»~~ — нет. Рецепт поллинга ограничен по времени и рассчитан на
  несколько повторных заходов в пределах TTL, так что повторная выдача подписки — не послабление,
  а требование.
