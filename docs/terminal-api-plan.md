# План: полный цикл планирования уведомления из терминала

Верхнеуровневый план к `docs/terminal-api-task.md`. Этапы идут в порядке зависимостей: 1–3 —
приведение существующего `POST /api/notifications` в состояние, пригодное для внешнего
потребителя; 4–5 — собственно pairing; 6–7 — приёмка и документация.

Схема БД не меняется ни на одном этапе — миграции (`docs/sqlite-migrations-task.md`) не нужны.
Учтено консолидированное ревью `docs/terminal-api-review-fable.md` (Fable 5 + два прохода
Opus 5).

## Этап 2. Валидация тела запроса и политика таймзон

Вся валидация этого этапа живёт **только на границе API (роутер)** — store не трогаем:
`validateDatetime` в store остаётся мягким (store не знает, кто его клиент), поэтому тесты
хранилища и `tests/tools.ts` не задеты.

- [ ] Модуль валидации `NotificationEntity`: `subscription.endpoint` — https-URL с hostname из
      allowlist известных push-сервисов (FCM, Mozilla, `web.push.apple.com`, WNS
      `*.notify.windows.com`), `keys.p256dh`/`keys.auth` — непустые строки, `payload` — объект,
      `datetime` — обязателен
- [ ] Лимит размера payload (~4 КБ — потолок Web Push) и `express.json({ limit })` в `src/app.ts`
      — лимит тела с запасом над payload (в том же JSON едут `subscription` и обвязка)
- [ ] Политика таймзон — в том же валидаторе на границе: требовать явную таймзону (`Z` или
      `±hh:mm`), отклонять голое `YYYY-MM-DDTHH:mm`; выверить, что браузерный клиент (шлёт
      `.toISOString()`) не задет
- [ ] Ответы на невалидное тело — `400` с JSON `{ "error": "…" }`, а не `text/plain`
- [ ] Unit-тесты валидации + интеграционные на `400`

## Этап 3. Лимиты

- [ ] **Разобраться с реальным IP клиента.** `nginx/pushka.conf` проксирует с `X-Real-IP`, но
      **без** `X-Forwarded-For`, а `trust proxy` в `src/app.ts` не выставлен — значит `req.ip`
      на проде равен `127.0.0.1` для всех запросов, и лимитер по IP молча станет глобальным.
      Либо добавить `X-Forwarded-For` в nginx + `app.set("trust proxy", …)`, либо читать
      `X-Real-IP` явно. Проверить на проде, а не только локально
- [ ] Мидлвар rate limit в памяти (окно + счётчик на IP) на `POST /api/notifications` и
      `POST /api/pair`, ответ `429` с JSON-телом (как и все ошибки API)
- [ ] Горизонт планирования: `datetime` не в прошлом (с допуском под `GRACE_MS`) и не дальше
      заданного потолка вперёд
- [ ] Интеграционные тесты: `429` при превышении, `400` при выходе за горизонт

## Этап 4. Pairing-сессии

`PUBLIC_ORIGIN` не заводим: `pairingUrl` в ответе не возвращаем, ссылку `<origin>/?pair=<id>`
собирает вызывающая сторона (решение и мотивировка — в task; формат ссылки — в README/OpenAPI).
Вместе с переменной исчезают правки `.env`/`env.ts`/`tests/env` и ручной шаг на проде.

- [ ] Хранилище сессий в памяти: `create()`, `get()`, `attachSubscription()`, TTL 10 минут;
      чистка протухших — лениво в `get()` плюс подметание при `create()`, без фонового таймера;
      кап `MAX_SESSIONS` (при переполнении `POST /api/pair` отвечает `503`)
- [ ] `src/router/pairRouter.ts` — три ручки:

| Метод | Путь                   | Ответ                                                                         |
| ----- | ---------------------- | ----------------------------------------------------------------------------- |
| POST  | `/api/pair`            | `201 { pairingId, expiresAt }` / `503` при переполнении                       |
| GET   | `/api/pair/:pairingId` | `200 { status: "pending" }` / `200 { status: "ready", subscription }` / `404` |
| PUT   | `/api/pair/:pairingId` | `204` / `400` на невалидный `subscription` / `404` для протухшей сессии       |

- [ ] `PUT` валидирует `subscription` тем же валидатором, что этап 2; повторный `PUT` на живую
      сессию — последний перезаписывает (два устройства открыли одну ссылку, страница шлёт
      `PUT` при каждой перезагрузке — это не ошибка)
- [ ] Подключить роутер в `src/router/router.ts`
- [ ] Unit-тесты хранилища сессий (в т.ч. протухание, кап) + интеграционные на все три ручки,
      включая негативный на `PUT` с мусорным `subscription`
