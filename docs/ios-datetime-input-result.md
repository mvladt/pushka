# Результат: фикс input[type=datetime-local] на iOS Safari (issue #12)

План — `docs/ios-datetime-input-plan.md`.

## Что сделано

В `<style>` в `src/client/index.html`, сразу после общего правила `input {}`, добавлен блок,
который снимает нативный вид `datetime-local` **только на iOS/iPadOS**:

```css
@supports (-webkit-touch-callout: none) {
  input[type="datetime-local"] {
    -webkit-appearance: none;
    appearance: none;
    display: block;
  }
  input[type="datetime-local"]::-webkit-date-and-time-value {
    text-align: left;
    min-height: 1.5em;
  }
}
```

Как это лечит issue: без `appearance: none` iOS Safari рисует поле собственным UA-виджетом,
который игнорирует `width: 100%` и `border`/`border-radius`/`background` из общего правила
`input {}` — отсюда и вылезание за колонку, и «другая» рамка на скриншоте из issue. Как только
нативный вид снят, поле подчиняется общим стилям формы наравне с «Заголовком» и «Текстом».
`::-webkit-date-and-time-value` компенсирует два побочных эффекта снятия нативного вида:
схлопывание пустого поля по высоте (`min-height: 1.5em` — это `line-height` из
`body { font: 16px/1.5 … }`) и центрирование значения (`text-align: left`).

Серверный код, тесты и деплой не затрагивались — диффом изменён только `src/client/index.html`.

## Отклонение от плана

План размещал правило `::-webkit-date-and-time-value` **вне** блока `@supports`. В реализации оно
внесено **внутрь** — по той же логике, из которой план исходил («минимальный радиус поражения»):
это правило существует только чтобы компенсировать последствия `appearance: none`, а `appearance:
none` применяется только на iOS. Вне iOS компенсировать нечего, и незачем трогать псевдоэлемент
нативного виджета в десктопном Chrome. Аргумент плана (правило вынесено отдельным блоком, чтобы
браузер, не знающий псевдоэлемент, не утащил при отбрасывании ничего нужного) при этом сохранён:
селектор по-прежнему живёт в отдельном правиле, а не через запятую с другими.

## Проверка

**Автоматическая (Chromium, замеры через Playwright).** Страница отрендерена в headless Chromium,
сняты `getBoundingClientRect()` и computed styles полей формы — на версии до фикса и после:

| Поле                  | До фикса          | После фикса       |
| --------------------- | ----------------- | ----------------- |
| `#input-title` (text) | 512 × 42          | 512 × 42          |
| `#input-body` (text)  | 512 × 42          | 512 × 42          |
| `#input-datetime`     | 512 × 44, `auto`  | 512 × 44, `auto`  |

Ни размеры, ни `appearance`, ни рамка на десктопе не изменились. `CSS.supports("-webkit-touch-callout",
"none")` в Chromium возвращает `false` — блок `@supports` там просто не применяется, что и
подтверждает нулевой радиус поражения на десктопе.

Отдельно прогнана сама iOS-ветка правил: из копии страницы убрана обёртка `@supports`, чтобы
правила применились в Chromium принудительно. Результат: `appearance: none` применён, ширина
поля осталась 512 (то есть равна ширине текстовых полей и колонки), рамка и радиус из общего
`input {}` сохранены, пустое поле по высоте не схлопнулось. Проверено также, что `min-height`
в Chromium ничего не ломает: с ним и без него высота одинаковая (44), пустое и заполненное поле
одной высоты — то есть правило безвредно там, где не нужно, и работает там, где нужно (iOS).

**CI.** Оба job'а `ci.yml` зелёные на коммите PR и на мёрдж-коммите `9a4bab2` в `main` — включая

получился «сначала прод, потом приёмка»: PR смержен, релиз `9a4bab234d3a` выкачен на прод ручным
`workflow_dispatch` (Deploy run #9, все шаги зелёные, `/api/health` → 200), после чего владелец
проверил страницу на iPhone и подтвердил, что поле «Время» выглядит как остальные. Issue #12
закрыт.
