# Ревью проекта Pushka — взгляд senior software engineer

_Дата: 2026-08-03. Ревью выполнено Claude (Fable 5) по запросу: оценить зрелость проекта,
сильные и слабые стороны, production-готовность, безопасность для хоста и пользователей,
соответствие SOLID/чистой архитектуре, уровень инженера._

---

## TL;DR

Для pet-проекта это неожиданно зрелая работа — не столько кодом, сколько **инженерной
культурой вокруг кода**: журнал решений, честный security-review самого себя, деплой с
релизами и откатом, pinned-by-SHA actions. Код при этом проще и сырее, чем обвязка: главные
слабости — отсутствие `strict` в TypeScript, отсутствие рантайм-валидации входа и открытый
write-эндпоинт, о котором вы сами знаете, но который так и не закрыт.

---

## Что хорошо (и это не дежурная похвала)

**Операционная зрелость выше, чем у многих коммерческих проектов такого размера:**

- `deploy/` — релизы по SHA, атомарное переключение симлинка `current`, хранение последних
  5 релизов, откат одной командой, `data/` (`.env` + база) вынесен из релизов. Это правильная
  схема, и в `deploy/README.md` внятно объяснено _почему_ именно так (симлинки на `.env` —
  чтобы деплой не перегенерировал VAPID-ключи и не убил подписки).
- GitHub Actions закреплены по полному SHA с Dependabot для обновления — реальная защита от
  supply-chain, которую большинство не делает.
- Узкий sudo для деплой-пользователя (`NOPASSWD` только на `systemctl restart pushka`),
  отдельный SSH-ключ для CI, отдельный системный пользователь. Принцип наименьших привилегий
  соблюдён.
- Приложение слушает `127.0.0.1`, наружу — только через nginx с HSTS, `nosniff`,
  `X-Frame-Options`.

**Культура принятия решений:**

- `docs/decisions.md` — лёгкий ADR-журнал с обоснованиями. Решение «не подключаем CodeQL»
  аргументировано конкретно: дефолтный taint-tracking не поймал бы ваши реальные дыры, потому
  что поток данных пересекает границу персистентности. Это верное и нетривиальное наблюдение.
- `docs/security-review-result.md` — честный разбор собственных уязвимостей с калибровкой
  серьёзности («слепой SSRF», «не амплификация, примерно 1:1»). Такое качество самокритики —
  редкость.

**В коде:**

- Чистый DI через фабрики: `store`, `pusher`, `logger` — интерфейсы, подменяемые в тестах.
  `createTestApp()` с in-memory SQLite — тесты изолированы и не оставляют мусора.
- Минимум зависимостей (3 прод-зависимости), нет build-шага — Node 24 стрипает типы сам.
  Это осознанный минимализм, а не лень.
- Нормализация `datetime` в канонический UTC-ISO, чтобы лексикографическое сравнение в SQL
  совпадало с хронологическим (`store.ts:59-61`) — правильное решение с комментарием-«почему».
- Grace-период для просроченных уведомлений (`scheduler.ts:6-10`) с внятным обоснованием.
- Клиент без фреймворка, XSS-безопасный (везде `textContent`, не `innerHTML`).

## Что плохо

**1. TypeScript без `strict` — самый большой промах на уровне кода.** В `tsconfig.json` нет
`"strict": true`, и это уже привело к вранью в типах: `getOneById` объявлен как
`Promise<NotificationEntity>`, а возвращает `undefined as unknown as NotificationEntity`
(`store.ts:73`). Это двойной каст, чтобы заставить компилятор замолчать — вместо честного
`NotificationEntity | undefined`. Ваши же тесты (`store.test.ts:79`) проверяют, что
возвращается `undefined`, то есть тип заведомо лжёт. Со strict-режимом компилятор бы это не
пропустил.

**2. Известные security-находки не закрыты.** Все пять чекбоксов в
`security-review-result.md` не отмечены. Вы сами написали «дешёвая точечная правка — стоит
взять раньше, чем откладывать надолго» — и отложили. Валидация тела + allowlist push-доменов
+ лимит параллелизма — это день работы, закрывающий главные риски.

**3. Ошибки валидации превращаются в 500.** `POST /api/notifications` с невалидным
`datetime`: `scheduler.schedule` → `store.saveOne` → `validateDatetime` кидает → Express 5
отдаёт **500** вместо **400**. Клиент видит «ошибка сервера» на свою же ошибку ввода.
Заодно: валидация живёт в слое хранилища — это неправильный слой, вход должен валидироваться
на границе (роутер). И сама `validateDatetime` слаба: `new Date("0")` — валидная дата
(2000 год), пройдёт.

**4. Scheduler — самая рискованная часть, и она не покрыта тестами.** Ни одного unit-теста
на `scheduler.ts`, при том что там вся бизнес-логика (grace-период, цикл). Конкретные
проблемы:

- `setInterval` с async-колбэком: если `work()` не успевает за `intervalMs` (медленный FCM),
  запускается второй проход по тем же записям → **дубли отправки**. Ваш же комментарий на
  `scheduler.ts:37` это признаёт.
- `removeMany(due)` выполняется после `sendMany` независимо от результата, а `sendOne`
  глотает все ошибки → семантика «максимум один раз, а может и ноль»: упавшая отправка тихо
  теряется навсегда. Для планировщика уведомлений это стоило бы хотя бы явно
  задокументировать как контракт.

**5. Мусор в роутере.** `GET/PATCH/DELETE /api/notifications/*` возвращают **500**
«Not implemented» — правильный код **501**. Внутри — закомментированный код и копипаста
«Received a PATCH» в GET-хендлере (`notificationRouter.ts:29`). Логирование полного тела
запроса конкатенацией строк каждые 2 секунды (`Scheduler work...`) засоряет journald на
проде — нет ни уровней логирования, ни фильтра.

**6. `cors()` без опций не нужен.** Клиент same-origin (раздаётся тем же процессом). Вы это
сами зафиксировали в находке 3 — уберите просто.

**7. E2E в CI ходит в реальный FCM** на каждый push. Это внешняя зависимость в CI: флаки,
зависимость от сети GitHub-раннеров, и небольшая, но ненулевая цена. Для smoke-теста
нормально, но было бы честно вынести в отдельный необязательный job или nightly.

## Production ready?

Смотря для чего. **Как демо/личный инструмент — да**, и это заявленный статус
(«демонстрационный проект» в README). **Как публичный сервис — нет**, по совокупности:

- открытый неаутентифицированный write-API без валидации и rate-limit;
- нет бэкапов SQLite (задача лежит в `docs/sqlite-backup-task.md` — вы знаете);
- нет мониторинга/алертинга — упавший сервис заметите вы, а не система;
- at-most-once доставка с тихой потерей при ошибках;
- `/api/health` не проверяет базу — вернёт 200 даже с мёртвым SQLite.

## Безопасность для вас как хоста

Изоляция сделана хорошо: непривилегированный пользователь, localhost-bind, узкий sudo.
Реальные риски — те, что вы сами нашли:

1. **Забивание диска** через открытый POST — SQLite растёт без лимита. VPS с забитым диском —
   это боль для _всех_ сервисов на нём, включая Xray.
2. **Абуз-риск для IP**: через `subscription.endpoint` любой может заставить ваш VPS слать
   POST-запросы куда угодно. Скоординированный залп → жалобы в Timeweb → риск блокировки IP.
   Для вас это, наверное, самый дорогой сценарий, потому что на том же IP живёт остальная
   инфраструктура.
3. Мелочь: в systemd-юните нет hardening-директив (`NoNewPrivileges=true`,
   `ProtectSystem=strict`, `PrivateTmp=true`, `ReadWritePaths=/srv/pushka/data`) —
   бесплатное сужение blast radius.

Дешёвая связка, закрывающая 1 и 2: `limit_req` в nginx + allowlist доменов endpoint
(`fcm.googleapis.com`, `web.push.apple.com`, `updates.push.services.mozilla.com`) + лимит
размера базы или количества записей.

## Безопасность для конечных пользователей

Здесь всё неплохо, потому что архитектура Web Push защищает пользователя сама: payload
шифруется end-to-end (web-push шифрует ключами `p256dh`/`auth` подписчика), push-сервис
содержимое не видит. Клиент XSS-безопасен. Уведомления удаляются после отправки — нет
накопления истории.

Два момента: (1) подписки и тексты уведомлений лежат в SQLite открытым текстом — при
компрометации сервера атакующий сможет слать пуши вашим подписчикам, пока подписки живы;
(2) чужую подписку невозможно угадать, так что «прислать пуш чужому человеку» через открытый
API нельзя — только тому, чей subscription-объект у тебя уже есть. Итог: риск для
пользователей низкий.

## SOLID / чистая архитектура / чистый код

По существу — **хорошо для своего размера, без карго-культа**:

- **DIP** — образцово: все зависимости через интерфейсы (`NotificationStore`, `WebPusher`,
  `Logger`), внедряются в фабрики, композиция в `main.ts`. Это самая сильная сторона кода.
- **SRP** — в основном да, с двумя нарушениями: валидация в store (должна быть на границе)
  и `createApp`, отдающий наружу `express` и `getPort` (ваш же TODO «нарушение
  инкапсуляции» — честно, но висит).
- **OCP/LSP/ISP** — не напрягаются и не нарушаются; для 10 файлов это правильно.
- Чистый код: читается легко, комментарии объясняют «почему» (это редкое умение), но есть
  мусор — закомментированный код, копипаст-логи, `TODO`, которые живут месяцами.

Отдельно скажу: отсутствие классов и слоёной архитектуры «по учебнику» — это _плюс_, а не
минус. Проект такого размера, размазанный по Controllers/Services/Repositories/DTOs, был бы
хуже.

## Ваш уровень как инженера

Вы попросили честно — честно и отвечу, с оговоркой: по истории проекта видно, что
значительная часть работы сделана в связке с агентом (issue-driven flow, доки в агентском
формате). Поэтому я оцениваю не «кто набрал код», а **качество решений и вкус** — их агент
за вас иметь не может.

- **Инженерное суждение и процесс — уверенный middle, местами выше.** Журнал решений с
  обоснованиями, отказ от CodeQL с конкретным аргументом вместо карго-культа, схема деплоя
  с пониманием _зачем_ каждая деталь, калиброванный security-review без паники и без
  замалчивания — это признаки зрелого мышления, которого нет у многих сеньоров. Умение
  сказать «риск реален, но низкий, вот почему» — дорогой навык.
- **Глубина кодинга — junior+/middle.** Выдают: неcтрогий tsconfig и двойной каст ради
  обмана компилятора, валидация не в том слое, 500 вместо 400/501, непокрытая тестами
  ядровая логика, известные дыры, откладываемые при цене в день работы. Это всё типичные
  точки роста именно этого уровня.
- **Главный паттерн, над которым стоит работать:** у вас разрыв между «знаю о проблеме» и
  «закрыл проблему». Проект полон точных самодиагнозов (TODO в scheduler,
  security-чекбоксы, TODO про инкапсуляцию) — и почти ни один не доведён до фикса.
  Диагностировать вы уже умеете лучше, чем средний джун; следующая ступень — дисциплина
  закрытия.

Так что «уровень невысокий» — слишком строго к себе. Вкус и системное мышление у вас
заметно опережают руки, а руки подтягиваются практикой быстрее, чем вкус.

# Часть 2: архитектура и system design — путь к «взрослому» высоконагруженному сервису

_Дописано 2026-08-10 по запросу: что улучшить архитектурно, чтобы проект стал более зрелым
и выдерживал высокую нагрузку._

## Текущая архитектура одним абзацем

Один Node-процесс делает всё: раздаёт статику, принимает HTTP, каждые 2 секунды поллит
SQLite (`datetime <= now`), шлёт пуши через `Promise.all` и удаляет записи независимо от
результата отправки. Состояние — один SQLite-файл, конфиг — self-writing `.env`. Это
честная и правильная архитектура для демо. Дальше — что и в каком порядке менять, если
растить её в нагруженный сервис.

## Что сломается первым под нагрузкой

Полезно понимать порядок отказов — он диктует приоритеты:

1. **Дубли и потери в планировщике** — не при нагрузке, а уже сейчас: перекрывающиеся
   `work()` дают дубли, удаление после `sendMany` без проверки результата даёт потери.
   Нагрузка лишь повышает вероятность.
2. **`Promise.all` без лимита параллелизма** — 10k due-уведомлений в одну секунду = 10k
   одновременных исходящих TLS-соединений = исчерпание файловых дескрипторов/памяти.
3. **SQLite под конкурентной записью** — `DatabaseSync` синхронный и блокирует event loop;
   без WAL-режима писатель блокирует читателей. Упрётся при сотнях RPS записи.
4. **Один процесс** — деплой/креш роняет и приём заявок, и отправку одновременно; CPU-ядра
   кроме одного простаивают.

## Ярус 0 — корректность (без этого масштабировать нечего)

Любое масштабирование дублирует и приумножает баги семантики доставки. Сначала — контракт.

**Жизненный цикл уведомления вместо «есть строка / нет строки».** Сейчас статус уведомления
неявный: наличие записи. Взрослая модель — явный статус:

```
pending → claimed → sent
                  → failed (retryable, с backoff и attempt_count)
                  → dead   (исчерпаны попытки / протухло)
```

Это одна миграция (`status`, `attempts`, `claimed_at`, `last_error`) и переписанный цикл
планировщика. Даёт: at-least-once вместо «как повезёт», историю для отладки, метрики
бесплатно (count по статусам).

**Клейм вместо чтения.** Ядро паттерна job queue — забирать работу атомарно:

```sql
UPDATE notifications SET status = 'claimed', claimed_at = ?
WHERE id IN (SELECT id FROM notifications
             WHERE status = 'pending' AND datetime <= ?
             ORDER BY datetime LIMIT 100)
RETURNING *;
```

Один такой запрос решает сразу три текущие проблемы: перекрывающиеся `work()` (второй
проход ничего не заклеймит), отсутствие батч-лимита (`LIMIT 100`), и потерю при падении
(незавершённый `claimed` со старым `claimed_at` возвращается в `pending` reaper'ом).

**Обработка ответов push-сервиса.** Сейчас `sendOne` глотает всё. Минимум: `404`/`410` —
подписка мертва, удалять и не ретраить; `429`/`5xx` — ретрай с экспоненциальным backoff;
остальное — в `dead` с сохранённой ошибкой. Плюс выставлять `TTL` в опциях `web-push` —
пусть push-сервис сам держит сообщение для офлайн-устройства, это бесплатная надёжность.

**Ограниченный параллелизм в `sendMany`.** Семафор на N одновременных отправок (свой в ~10
строк, без библиотеки) + keep-alive агент для исходящих соединений к FCM/APNs — иначе
каждый пуш платит за новый TLS-handshake.

## Ярус 1 — зрелость на одной машине (докуда реально доехать на VPS)

**Разделить роли: API-процесс и worker-процесс.** Первый настоящий шаг к взрослости — не
Kubernetes, а два systemd-юнита вместо одного:

```
pushka-api.service     — HTTP: приём заявок, отдача ключа, статика
pushka-worker.service  — цикл: клейм → отправка → ретраи
        └── общаются только через БД (транзакционный outbox по сути)
```

Что это даёт: деплой/креш API не останавливает отправку и наоборот; можно рестартить,
скейлить и мониторить независимо; воркер можно остановить для обслуживания БД, а приём
заявок продолжится. Код почти не меняется — `main.ts` разъезжается на два entrypoint'а с
той же композицией фабрик. Ваша DI-структура к этому уже готова — это её главная награда.

**SQLite настроить, а не менять.** До миграции на «настоящую» БД SQLite тянет сильно
больше, чем принято думать (десятки тысяч записей/сек в WAL-режиме):

```
PRAGMA journal_mode = WAL;      -- писатель не блокирует читателей
PRAGMA busy_timeout = 5000;     -- вместо мгновенного SQLITE_BUSY
PRAGMA synchronous = NORMAL;    -- честный компромисс для WAL
```

Плюс составной индекс `(status, datetime)` под клейм-запрос — текущий индекс только по
`datetime` перестанет помогать после появления статусов.

**Наблюдаемость — предусловие «высоконагруженности», а не опция.** Нельзя управлять тем,
что не измеряешь. Минимальный набор:

- структурные логи с уровнями (`pino` — одна зависимость; текущий `console.log` каждые 2
  секунды — это анти-наблюдаемость, шум, скрывающий сигнал);
- метрики (`prom-client`, эндпоинт `/metrics` только на localhost): глубина очереди по
  статусам, **лаг планировщика** (now − datetime самого старого pending — главная метрика
  сервиса, это и есть его SLO), латентность и коды ответов push-сервисов, счётчик ретраев;
- `/api/health` должен проверять БД (сейчас вернёт 200 при мёртвом SQLite);
- алертинг поверх — хоть простой скрипт в cron, который дёргает `/metrics` и шлёт… push :)

**Конфиг по 12-factor.** Self-writing `.env` — милая фича для демо, но во взрослом сервисе
процесс не должен иметь права писать собственный конфиг (и генерация новых VAPID-ключей при
потере файла — это тихая катастрофа, убивающая все подписки; лучше громко упасть).
Читать из окружения (`EnvironmentFile=` в systemd), падать при отсутствии ключей,
генерацию вынести в отдельный явный скрипт `npm run generate-vapid`.

**API-зрелость:** версионирование (`/api/v1/…`), рантайм-валидация на границе (по вкусу:
`zod` или ручная — но на границе, не в store), аутентификация write-эндпоинтов (API-ключ в
заголовке — достаточно), rate-limit (можно целиком в nginx: `limit_req`), и honest-коды
(`400`/`401`/`429`/`501`). Заглушки CRUD либо реализовать, либо удалить — недо-эндпоинты
хуже отсутствующих.

## Ярус 2 — горизонтальный масштаб (когда одной машины мало)

Сюда стоит идти только по показаниям метрик из яруса 1, не заранее.

**SQLite → PostgreSQL.** Триггер перехода: больше одной машины ИЛИ воркеров-процессов
больше, чем комфортно одной SQLite-базе. Паттерн клейма переносится дословно и становится
каноническим:

```sql
SELECT ... FROM notifications
WHERE status = 'pending' AND datetime <= now()
ORDER BY datetime LIMIT 100
FOR UPDATE SKIP LOCKED;
```

`SKIP LOCKED` — это то, ради чего затевался ярус 0: N воркеров на разных машинах
конкурентно разбирают одну очередь без координатора, без дублей, без внешнего брокера.
Ваша абстракция `NotificationStore` делает миграцию заменой одной фабрики — интерфейс уже
правильный.

**Дальше по необходимости, в порядке возрастания сложности:**

- API — stateless, N реплик за nginx'ом (уже почти так: единственное состояние — БД);
- воркеры — N реплик, масштабируются по метрике лага планировщика;
- выделенная очередь (Redis + BullMQ) — только если Postgres-очередь упрётся (это
  миллионы job'ов в день; у большинства проектов этот день не наступает);
- шардирование по времени/пользователю — за горизонтом разумного для этого проекта.

**Чего НЕ делать** (тот же минимализм, только на уровне архитектуры): микросервисы дальше
разбивки api/worker, Kafka, Kubernetes, event sourcing. Связка «Postgres + stateless API +
воркеры со SKIP LOCKED» — это архитектура, на которой живут прод-системы с миллионами
отложенных задач в день. Для push-планировщика её потолок практически недостижим.

## Целевая картина

```
                        ┌────────────────────┐
  Клиенты ──HTTPS──▶ nginx (TLS, rate-limit) │
                        └───────┬────────────┘
                                ▼
                    pushka-api ×N (stateless)
                     валидация, auth, приём
                                │ INSERT (pending)
                                ▼
                     БД: SQLite/WAL → Postgres
                     статусы, попытки, outbox
                                ▲
                                │ claim (SKIP LOCKED) / retry / reap
                    pushka-worker ×N
                     семафор параллелизма,
                     backoff, обработка 410
                                │
                                ▼
                     FCM / APNs / Mozilla autopush
```

## Порядок внедрения (каждый шаг ценен сам по себе)

1. Статусная модель + клейм-запрос + обработка `410`/ретраи + лимит параллелизма (ярус 0
   целиком — это одна связная переработка scheduler+store+pusher).
2. WAL + `busy_timeout` + индекс `(status, datetime)`.
3. Разделение на api/worker процессы (два entrypoint'а, два systemd-юнита).
4. pino + prom-client + честный health + метрика лага.
5. Валидация/auth/rate-limit на границе.
6. Postgres — только когда метрики скажут, что пора.

Пункты 1–2 устраняют реальные баги и стоят дёшево. Пункты 3–5 — та самая «взрослость».
Пункт 6 — по показаниям. В сумме это ровно тот трек, по которому эволюционирует любой
серьёзный планировщик задач, — просто пройденный осознанно и без карго-культа.
